# 规格：远程 Neo4j MCP 工具可见性收敛

## 问题陈述

GitNexus 的远程 Neo4j Docker 部署通过内嵌 MCP 端点供 LLM 查询代码知识图谱。当前部署暴露完整工具面，其中包含原始 Cypher、重命名、分组同步和跨组路由等不适合该查询型服务的能力。即使这些能力不被正常使用，它们仍增加模型选择错误工具、生成越权调用和维护复杂度的机会。

## 解决方案

仅在远程 Neo4j Docker 部署中显式启用现有 MCP 只读策略。该策略会在工具发现阶段隐藏不允许的能力，并在工具调用阶段拒绝绕过发现列表的直接调用；保留已有的只读查询工具面。

本地 stdio MCP、独立 MCP HTTP、CLI 命令和普通 Web/API 运行方式保持当前行为。Neo4j 仅继续作为存储后端选择，不作为全局 MCP 权限开关。

## 用户故事

1. 作为使用远程 GitNexus MCP 的 LLM，我希望只看到可安全查询的工具，以便减少选择错误或不可用工具的概率。
2. 作为使用远程 GitNexus MCP 的 LLM，我希望能够继续列出仓库、查询代码、查看符号上下文、分析影响范围和追踪调用路径，以便完成代码理解任务。
3. 作为远程服务管理员，我希望即使客户端手工提交隐藏工具名称，服务仍拒绝调用，以便工具收敛不是仅靠客户端界面约定。
4. 作为远程服务管理员，我希望原始 Cypher、重命名和分组管理能力不出现在远程查询 MCP 的工具列表中，以便降低操作性风险。
5. 作为本地 GitNexus 用户，我希望 stdio MCP、CLI 和本地开发行为不因远程 Neo4j 部署策略而改变，以便维持既有工作流兼容性。
6. 作为维护者，我希望 Neo4j 存储后端配置与 MCP 权限策略保持解耦，以便未来可在任意存储后端按部署需求启用只读 MCP。
7. 作为测试维护者，我希望现有只读策略的发现与调用拒绝行为继续作为回归基线，以便部署配置变更不会削弱安全边界。

## 实现决策

- 以远程 Docker 部署配置为唯一实现 seam，显式启用现有只读 MCP 策略。
- 不新增按工具名称配置的白名单，不新增新的 MCP 策略类型，不改动工具注册、dispatch 或 Neo4j backend 判断逻辑。
- 保持既有只读策略定义的查询工具可见性；其隐藏、资源清理、group 路由限制和调用拒绝语义均保持不变。
- 只影响远程部署经内嵌 MCP 端点提供的工具面；不改变本地和其他运行模式的默认环境变量。
- 远程部署可以在未来按独立需求叠加仓库 allowlist/default repo，但本次不改变仓库范围策略。

## 测试决策

- 以 MCP 协议外部行为为准：工具发现不包含被隐藏能力，直接调用被隐藏能力被拒绝，允许的查询工具仍正常可发现和调用。
- 复用现有只读 MCP 策略测试作为主要行为覆盖，避免为 Docker 配置复制工具注册或 dispatch 测试。
- 增加或更新部署配置验证，确认远程 Neo4j 服务会向运行容器传递只读策略环境变量。
- 验证范围覆盖远程部署配置解析与现有 MCP 只读策略；不启动真实远端服务、不调用生产仓库、不测试 LLM 本身。

## 范围外

- 不引入精确的工具名称 allowlist。
- 不改变工具实现、Neo4j 查询逻辑、MCP HTTP 协议、认证机制或资源模型。
- 不修改 stdio MCP、独立 HTTP MCP、CLI 或普通 Web/API 的默认工具可见性。
- 不配置仓库 allowlist、默认仓库或单仓库限制。
- 不在本次处理中部署、提交或推送。

## 补充说明

现有只读策略已覆盖发现层与调用层，因此优先复用该机制比新增“隐藏列表”更能防止客户端绕过。该策略由远程部署显式启用，避免把存储类型误当作权限模型。
