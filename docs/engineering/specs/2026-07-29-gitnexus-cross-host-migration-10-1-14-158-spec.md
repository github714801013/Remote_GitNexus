# GitNexus 跨主机迁移至 10.1.14.158 规格

## Problem Statement

当前 GitNexus 的应用、完整项目源文件、模型文件、运行元数据、Zoekt 索引与 Neo4j 图库运行在 `10.1.14.177`。需要将这一整套可查询能力迁移到 `10.1.14.158`，并使迁移后的持久化数据全部落在目标机 `/data1`。

迁移必须避免覆盖目标机现有的 Dify Neo4j 服务及其数据，同时保留源端的实际运行应用版本、完整图数据、索引、数据库元数据与认证身份。调用方需要在验收完成后统一切换至新的 MCP 和 Neo4j 入口，并在出现问题时可以在保留期内安全回滚，避免双活导致的数据分叉。

## Solution

采用两阶段迁移和短暂停机切换：先在源端服务运行期间预同步项目、模型、运行元数据、Zoekt 索引及 Neo4j 数据初始副本；在 Asia/Shanghai 22:00 后的 60 分钟维护窗口停止源端 GitNexus 与 Neo4j，完成最终增量同步和完整 Neo4j 卷复制，在目标端以源端相同的应用镜像摘要及固定 `neo4j:2026.04.0` 启动独立 Compose 服务。

目标端使用 `/data1/gitnexus` 作为唯一持久化根目录，应用容器继续将项目目录挂载为 `/projects`。目标端 MCP 统一入口为 `http://10.1.14.158:1347/api/mcp`，保留 `1350`；Neo4j 使用目标机未占用的 `7475` 和 `7688` 映射，避免与 Dify 已占用的 `7474` 和 `7687` 冲突。只有在目标端完成数据库、索引、MCP 同会话协议和调用方实际查询验收后，才更新 cc-switch、已识别 MCP 调用方及已发现的 Neo4j 直连调用方。

## User Stories

1. 作为 GitNexus 使用者，我希望服务迁移到 `10.1.14.158` 后仍能通过 MCP 检索代码，以便不改变日常代码分析流程。
2. 作为平台维护人员，我希望迁移后的所有持久化数据放在 `/data1`，以便避免占满目标机根分区并统一管理备份和容量。
3. 作为代码检索使用者，我希望完整迁移项目源目录，而不是仅迁移部分仓库，以便保留既有跨项目检索范围。
4. 作为 GitNexus 使用者，我希望容器内项目目录仍然是 `/projects`，以便既有运行配置和索引路径语义保持兼容。
5. 作为维护人员，我希望目标端运行源端当前正在使用的相同应用镜像摘要，以便迁移不夹带本地脏工作区中的未发布代码。
6. 作为维护人员，我希望迁移模型文件和 GitNexus 运行元数据，以便目标端能够按源端能力启动和提供查询。
7. 作为代码检索使用者，我希望 Zoekt 索引随服务迁移，以便切换后全文和符号检索无需重新建立全部索引。
8. 作为图查询使用者，我希望完整迁移 Neo4j 数据卷，以便保留图数据、索引、数据库元数据、用户和认证身份。
9. 作为维护人员，我希望目标端固定使用与源端兼容的 `neo4j:2026.04.0`，以便卷数据能够安全恢复。
10. 作为目标机现有服务的维护人员，我希望 GitNexus 使用独立的 Compose 项目、容器和数据目录，以便不影响 `dify-neo4j`。
11. 作为 Dify 使用者，我希望目标机原有 `7474` 和 `7687` 端口继续可用，以便 GitNexus 迁移不会中断 Dify 的 Neo4j 访问。
12. 作为 Neo4j 直连调用方，我希望通过 `10.1.14.158:7475` 和 `10.1.14.158:7688` 访问 GitNexus Neo4j，以便端口映射明确且不会发生服务混淆。
13. 作为 MCP 调用方，我希望在切换后通过 `http://10.1.14.158:1347/api/mcp` 访问 GitNexus，以便所有调用方使用统一的新入口。
14. 作为兼容旧配置的调用方，我希望 `1350` 继续保留，以便不破坏已知的辅助入口或既有网络契约。
15. 作为维护人员，我希望在正式停机前完成在线预同步，以便将实际维护窗口压缩到最终增量与验收所需时间。
16. 作为维护人员，我希望最终同步前停止源端 GitNexus 和 Neo4j，以便避免源端和目标端同时写入导致图数据或索引分叉。
17. 作为业务使用者，我希望维护窗口安排在 Asia/Shanghai 22:00 后，以便降低切换对正常工作时间的影响。
18. 作为维护人员，我希望维护窗口预留 60 分钟，以便有足够时间完成最终同步、启动、验证和必要回滚。
19. 作为安全负责人，我希望私密运行配置通过 SSH 加密传输并只落在目标端 root 私有目录，以便密钥、Token 和密码不进入仓库、日志或聊天记录。
20. 作为安全负责人，我希望目标端私密配置仅 root 可读，以便限制运行凭据暴露面。
21. 作为 cc-switch 使用者，我希望切换后 cc-switch 指向新 MCP 地址并能完成实际查询，以便配置变更得到真实端到端验证。
22. 作为已识别 MCP 调用方的维护人员，我希望在验收通过后切换到新地址，以便避免调用方仍访问已停止的源端。
23. 作为已发现 Neo4j 直连调用方的维护人员，我希望其连接地址更新为目标端新端口，以便直连查询不落到 Dify Neo4j 或旧主机。
24. 作为维护人员，我希望未发现的静态调用方不被猜测性修改，以便避免对未知系统造成无证据的配置破坏。
25. 作为迁移验收人员，我希望目标端 MCP 和 Neo4j 容器都健康，以便确认服务已实际启动。
26. 作为迁移验收人员，我希望确认 Neo4j 版本、数据库在线状态和基础 Cypher 查询，以便确认迁移的是可用图库而非仅有容器进程。
27. 作为代码检索使用者，我希望用 `list_repos(isall=true)` 与源端仓库清单比对，以便确认迁移后的索引覆盖范围完整。
28. 作为 MCP 协议调用方，我希望在同一会话中完成 initialize、initialized、tools/list 和 query，以便确认会话状态、工具挂载和查询路径完整可用。
29. 作为 oa-stock 使用者，我希望 `repo=oa-stock, search_query=PaoTuiListener` 的已知查询在目标端成功，以便验证真实业务检索能力。
30. 作为网络维护人员，我希望确认 `1347`、`1350`、`7475` 和 `7688` 都可达，以便确认服务入口、辅助入口和图库端口可用。
31. 作为维护人员，我希望切换后源端服务保持停止，以便避免在两个主机上同时提供可能不一致的数据。
32. 作为风险控制人员，我希望源端应用、项目、Neo4j 卷、Zoekt 索引和镜像保留 7 天，以便在发现问题时能够恢复。
33. 作为维护人员，我希望回滚时可以恢复调用方地址并重新启动源端服务，以便有清晰、可执行的恢复路径。
34. 作为变更审计人员，我希望迁移记录明确标识完成项、验收证据、未验证项和风险，以便后续追踪和复盘。
35. 作为仓库维护人员，我希望迁移实施不混入当前工作区无关修改，以便后续代码交付保持最小且可审计的变更范围。

## Implementation Decisions

- 使用两阶段迁移：在线预同步后，在已确认维护窗口内停源端完成最终增量同步与启动切换。
- 目标端的持久化根目录固定为 `/data1/gitnexus`，包含应用运行配置、项目源文件、模型、运行元数据、Neo4j 数据与日志、Zoekt 索引等独立子目录。
- 迁移完整项目目录，而非基于 allowlist 或已知仓库列表裁剪内容；容器内仍挂载到 `/projects`。
- 目标端应用必须复用源端实际运行镜像的固定摘要，不从当前本地未提交工作区构建或替换运行版本。
- Neo4j 固定采用 `neo4j:2026.04.0`，最终停机窗口复制完整数据卷和日志卷，以保留图、索引、数据库元数据及认证身份。
- 目标端 GitNexus 与现有 Dify 服务完全隔离：独立 Compose 项目、容器、卷/宿主机目录和端口，不覆盖、停止、修改 Dify 的 Neo4j 容器或数据。
- GitNexus Neo4j 的宿主机端口固定映射为 `7475 -> 7474` 和 `7688 -> 7687`；不得占用目标机 Dify 使用的 `7474/7687`。
- MCP 的切换入口固定为 `http://10.1.14.158:1347/api/mcp`，`1350` 继续暴露；源端不保留转发代理。
- 迁移期间私密运行配置仅通过加密通道传输到目标端 root 私有目录；不得读取、打印、提交或写入任何秘密值。
- 调用方修改范围限于 cc-switch、已识别 MCP 调用方和已发现的 Neo4j 直连调用方；未发现的调用方作为已知风险记录，不实施猜测性修改。
- 调用方配置只在目标端全部阻塞验收通过后更新；切换后源端服务保持停止，防止双活和数据分叉。
- 源端数据、卷、镜像和项目目录保留 7 天；删除、清理或永久下线需要在回滚期结束后另行授权。
- 实施、配置和交付必须使用明确文件范围，避免把当前工作区的无关未提交内容纳入迁移或后续 Git 提交。

## Testing Decisions

- 测试以外部可观察的迁移结果为准，不以单个同步命令或容器创建成功代替业务验收。
- 在切换调用方前，验证目标端 GitNexus MCP 和 Neo4j 容器健康，并确认端口 `1347`、`1350`、`7475`、`7688` 可达。
- 验证 Neo4j 运行版本为 `2026.04.0`、目标数据库在线，并执行基础只读 Cypher 查询确认图数据可访问。
- 在源端和目标端执行 `list_repos(isall=true)` 并比对仓库及索引状态，确认 Zoekt 与仓库索引迁移完整。
- 使用同一个 Streamable HTTP MCP 会话按顺序验证 initialize、notifications/initialized、tools/list 和 query，确认工具不是仅在资源接口层可见。
- 回归已知业务查询：在 `oa-stock` 范围查询 `PaoTuiListener`，结果必须能够证明目标端代码检索路径实际工作。
- 在更新 cc-switch 后，从 cc-switch 发起一次真实 MCP 查询，证明配置、网络、会话 Header 和目标服务集成均已生效。
- 验证源端服务停止后不存在双活；同时验证回滚操作所需的源端服务启动与调用方配置回切步骤可执行，但不在验收成功时主动回滚。
- 对每个验证记录命令、时间、脱敏结果和通过/失败状态；不得记录私密配置内容。

## Out of Scope

- 在迁移期间修改 GitNexus 业务功能、从本地脏工作区构建新镜像或发布新代码。
- 覆盖、停止、升级或重配置目标端既有 Dify/Neo4j 服务及其数据卷。
- 通过仅导出业务节点和关系后重建 Neo4j 用户、认证或索引来替代完整卷迁移。
- 在源端保留长期转发代理，或在切换成功后让源端和目标端同时运行 GitNexus/Neo4j。
- 猜测性修改未盘点到的调用方配置。
- 迁移过程中删除源端项目、卷、索引、镜像或私密配置。
- 将密钥、密码、Token 或真实环境配置写入仓库、Issue、日志、测试数据或聊天记录。
- 本规格阶段执行实际迁移、停止源端服务、修改调用方生产配置、提交或推送代码；这些动作需要在实施阶段按授权执行。

## Further Notes

- 源端为 `10.1.14.177`，目标端为 `10.1.14.158`；目标机 `/data1` 已确认适合作为迁移数据位置。
- 目标机已经存在 `dify-neo4j`，其宿主机 `7474/7687` 端口和独立数据必须保持不变。
- 源端运行的 GitNexus MCP 相关端口为 `1347/1350`；目标端迁移后沿用这两个 MCP 端口，并使用新的主机地址。
- 源端应用、项目目录和索引的实际体量较大，最终维护窗口前的预同步应明确统计传输结果和最终增量。
- 当前仓库工作区已有大量与迁移规格无关的修改和未跟踪文件；规格文档与后续实施变更必须使用显式 allowlist，禁止 `git add .`。
- 本规格依据已确认的迁移发现、需求基线和 ADR-0004；实施前应重新核验会变化的远端容量、端口占用、容器状态和调用方配置。
